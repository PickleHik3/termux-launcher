# LiteRT / LiteRT-LM on-device LLM: termux-launcher vs. opendroid

Assessment date: **2026-09-21**. Local checkout (termux-launcher, branch `dev`): **9dc4ff2cbc287271636aeeea8f165e6be550ccc6**. `opendroid` checkout: shallow clone of `https://github.com/yashab-cyber/opendroid`, commit **6ff5a061755b597b0558fed1f565587837ed4d51** (default branch at clone time, read-only, cloned into the session scratchpad, not committed to this repo). This is a research comparison, not an implementation plan; no code was changed, built, installed, or run on a device.

## What opendroid is

Per its own README, opendroid is "the Open-Source Autonomous AI Agent for Android" — a phone agent that plans, executes and verifies multi-step actions (accessibility automation, notifications, messaging) — not a launcher. [`opendroid README.md:1-45`]. Its LLM layer is one subsystem among several (accessibility service, notification listener, voice/wake-word service — see `app/src/main/AndroidManifest.xml:77-138`), used to drive that agent loop, not to power an assistant surface that is itself the product as in termux-launcher's TAI.

## Finding

Both projects depend on the **exact same LiteRT-LM artifact and version** — `com.google.ai.edge.litertlm:litertlm-android:0.14.0` (opendroid: `app/build.gradle:263`; termux-launcher: `app/build.gradle:12,172`) — and both call its `Engine`/`Conversation` Kotlin/Java API rather than MediaPipe LLM Inference or raw TFLite for text generation. Beyond that shared dependency the two integrations diverge sharply in maturity: termux-launcher runs the engine in an isolated `:tai_runtime` process with a persisted crash marker, RAM-tiered context-window sizing, native `ToolCall`/`Channel` (thinking-channel) API usage, KV-cache-aware conversation reuse, and image+audio multimodal backend selection; opendroid runs LiteRT-LM in the app's main process with a two-backend (GPU→CPU) fallback, no NPU path despite advertising one, and implements "tool calling" by asking the model to emit JSON in its own prompt template rather than using LiteRT-LM's native tool-call surface. Conversely, opendroid has a materially more rigorous **download-integrity** subsystem (pinned revision + mandatory SHA-256 before a catalog entry is even considered downloadable) than the one file in scope on the termux-launcher side (`TaiArtifactCompatibility.java`, which only does semver comparison for minimum-runtime checks).

Both pin LiteRT-LM 0.14.0 (released 2026-07-08 per GitHub Releases), five minor versions behind the current upstream release **v0.17.1** (2026-09-16) as of this writing — an upstream fact, not a claim about either app's roadmap. [github.com/google-ai-edge/LiteRT-LM/releases, fetched 2026-09-21]

## Prose per axis (points not fully captured in the table)

**API surface.** Neither project uses MediaPipe's LLM Inference API or raw TFLite for text generation; both call LiteRT-LM's `Engine`/`Conversation` Kotlin/Java surface directly. termux-launcher additionally imports `ToolCall` and `Channel` from the SDK (`LiteRtTaiRuntime.java:10,21`) — types Google's docs describe as part of LiteRT-LM's "Tool Use APIs" and reasoning/thinking-channel support introduced in the 0.14.0 release note ("Tool Calling & Agentic Capabilities... support for reasoning/thinking channels", per GitHub Releases, fetched 2026-09-21) — while opendroid's `LiteRTLMProvider.kt` imports neither.

**Model acquisition.** Both resolve models from Hugging Face URLs; opendroid's registry hard-codes four Gemma/Qwen catalog entries with pinned commit-revision download URLs (`OnDeviceModelRegistry.kt:149-252`). This comparison did not read termux-launcher's `TaiModelDownloader`/`TaiModelCatalog` (out of scope per the brief), so its catalog breadth is not directly re-verified here; see the repo's own prior note for that (`project-docs/tai-model-ecosystem-research.md`).

**Multimodal.** opendroid's README and `OnDeviceBackend`/registry naming suggest multimodal is intended to go through the ML Kit "AI Core" (`GemmaProvider.kt`) path, not LiteRT-LM; no image/audio-specific code was found inside `LiteRTLMProvider.kt` itself.

**MNN sibling (context only, per the brief).** termux-launcher's `MnnTaiRuntime.java` (1284 lines) is a second on-device text backend built on Alibaba's MNN `LlmSession`, sharing the same `Content`/`Message` wire types from `com.google.ai.edge.litertlm` for its JSON transcript format (`MnnTaiRuntime.java:11-12`) but running an entirely different (non-LiteRT) inference engine; opendroid has no equivalent second local-inference backend — its "hybrid" split is LiteRT-LM vs. Google's cloud/on-device ML Kit GenAI API, not two independent local runtimes.

## What termux-launcher could take from opendroid

- **Mandatory, structured download-integrity metadata.** opendroid's `ManagedModelArtifactMetadata.isComplete` refuses to treat an artifact as downloadable unless it carries a pinned 40-hex Hugging Face revision, a positive expected size, and a SHA-256 value together (`ModelArtifactIntegrity.kt:16-40`) — a stricter, type-enforced default than termux-launcher's SHA-256 check being described as "optional" in the repo's own prior research note (`project-docs/tai-model-ecosystem-research.md`).
- **A single explicit backend-compatibility probe class.** `LiteRtCompatibility.verify()` isolates "can this file even initialize an `Engine` on this device" into one reusable, testable function with an explicit distinction between a malformed artifact and a device/backend limitation (`LiteRtCompatibility.kt:18-56`); this is a narrower, more directly testable unit than doing the equivalent logic inline during a full model load.
- **GGUF-format rejection at the filename layer.** `ModelStoragePaths.isLikelyUnsupportedGguf` gives a clear, cheap early rejection message for a common but unsupported import format before any download/parse attempt (`ModelStoragePaths.kt:52-54`).

## What opendroid lacks that termux-launcher has

- **Process isolation for the inference engine.** opendroid runs `Engine`/`Conversation` in the app's main process (no `android:process` on any manifest `<service>`, `AndroidManifest.xml:63-141`); a native crash inside the LiteRT-LM JNI layer would take down the whole app, whereas termux-launcher isolates it in `:tai_runtime` (`AndroidManifest.xml:355-358`).
- **A pre-load memory guard.** termux-launcher's `TaiLoadPreflight` hard-blocks a load when available memory is below a 512 MiB threshold or the system reports low memory (`TaiLoadPreflight.java:23,271-293`); no equivalent pre-load check was found in opendroid — it relies on `android:largeHeap="true"` plus reactive string-matching of "OOM" in a caught exception (`providers/LiteRTLMProvider.kt:505-509`).
- **A load-crash marker that survives process death.** `TaiRuntimeCrashMarker` persists "a load is in progress" to `SharedPreferences` before `Engine` construction and clears it after, so a hard crash during load can still be reported on the next launch (`TaiRuntimeCrashMarker.java:18-45`); nothing equivalent was found in opendroid.
- **Native tool-calling and thinking-channel support.** termux-launcher reads `ToolCall` objects and configures `Channel`s (e.g. a "thought" channel) directly from the LiteRT-LM SDK (`LiteRtTaiRuntime.java:349,965-990`); opendroid emulates tool calling by asking the model to emit JSON in-band and hand-parsing it (`providers/LiteRTLMProvider.kt:211-215`), which depends on the model reliably following that prompt convention rather than a structured SDK contract.
- **Device-RAM-tiered, KV-cache-aware context sizing.** `TaiContextWindowPolicy` scales the engine's token budget to the device's RAM tier and reuses a `Conversation` (preserving its KV cache) only when a fingerprint check proves the new request is a strict continuation of the prior transcript (`TaiContextWindowPolicy.java:22-46`, `LiteRtTaiRuntime.java:721-758`); opendroid uses one fixed `contextWindow` per catalog entry with no device-memory scaling and no conversation-reuse/fingerprint logic found.
- **Multimodal (image/audio) input on the LiteRT-LM path itself.** termux-launcher selects a separate vision backend and forces audio input to CPU inside the same `LiteRtTaiRuntime` (`LiteRtTaiRuntime.java:809-827`); opendroid's `LiteRTLMProvider.kt` has no image/audio handling — multimodal there is routed to a different provider (ML Kit GenAI), not LiteRT-LM.
- **NPU backend attempt.** termux-launcher's code comments explicitly reference LiteRT-LM 0.14's GPU/NPU acceleration for audio (`LiteRtTaiRuntime.java:824`) even though it defaults to CPU there; opendroid's backend list is GPU-then-CPU only (`LiteRtCompatibility.kt:24-26`) despite its own doc comment claiming GPU/NPU support (`providers/LiteRTLMProvider.kt:32`) — i.e., neither app has a working NPU path today, but only termux-launcher's code acknowledges the SDK capability in a way that looks toward adding it.

## Planning loop and generation path

Same sources and rules as above: read-only, primary sources, file:line citations, no build/device use, not committed. opendroid hash `6ff5a061755b597b0558fed1f565587837ed4d51`; termux-launcher `dev` at `9dc4ff2cbc287271636aeeea8f165e6be550ccc6`.

### opendroid: the planner, the executor, the verifier

The planner is `com.opendroid.ai.core.agent.AgentLoop` (1793 lines), backed by `PlanManager.kt` (318 lines, plan/step state), `ActionSequenceExecutor.kt` (152 lines, dispatch + parameter resolution), `ReEvaluationEngine.kt` (260 lines, failure replanning + conditional-step evaluation), and the prompt templates in `core/llm/prompts/PlanningPrompts.kt` (109 lines) and `ReEvalPrompts.kt`.

- **System prompt / step schema.** `PlanningPrompts.buildPlanningPrompt()` builds the planning system prompt from `ActionSchema.buildPlanningSchema()` so the whitelist of ~N callable actions is generated, not hand-maintained, and spells out rules such as never inserting `OPEN_APP` before a "self-contained" action and always following a `TYPE_TEXT` into a search box with `PRESS_ENTER` [`PlanningPrompts.kt:9-79`]. A step is the `PlanStep` data class: `stepId`, `order`, `description`, `action`, `params: Map<String,String>`, `dependsOn`, `canParallelize`, `fallback`, mutable `status`/`result`/`error` [`data/models/PlanStep.kt:6-19`]. The model is told to return one JSON object of shape `{goal, planId, estimatedSteps, estimatedDuration, steps:[...]}` matching `data/models/Plan.kt:6-14` [`PlanningPrompts.kt:81-97`].
- **One call per plan, not per step.** `generatePlan()` sends the *entire* user goal once and expects the *entire* multi-step plan back as one JSON blob via `provider.complete(LLMRequest(responseFormat = ResponseFormat.JSON, maxTokens = 1500, temperature = 0.1f))` — a single non-streaming call [`AgentLoop.kt:628,693-703`]. If `settingsRepository.llmConfig` has `multiAgentModeEnabled`, two more calls run first: a planner call and, concurrently, a "Safety and Security Critic" call against `PlanningPrompts.CRITIC_SYSTEM_PROMPT` (temperature 0.2, `ResponseFormat.TEXT`), then a third "Plan Merger" call combines both into the final plan JSON (`PlanningPrompts.MERGE_SYSTEM_PROMPT`, temperature 0.1) [`AgentLoop.kt:634-692`, `PlanningPrompts.kt:99-108`]. The raw text is stripped of markdown fences and parsed into a `Plan` by `parsePlanFromLlmResponse()`/`cleanPlanJson()` [`AgentLoop.kt:1575-1703`].
- **Executor.** `executePlanLoop()` is a `while(true)` loop with no LLM call in the common path: it takes `planManager.getActiveStep()`, resolves `$stepId`-style parameter references from prior steps' results via `actionSequenceExecutor.resolveParameters()`, and dispatches the step's `action` string to `actionSequenceExecutor.dispatch(...)`, which maps to real device-automation code (accessibility clicks, `Intent`s, etc.) [`AgentLoop.kt:945-993`].
- **Verifier / re-evaluation.** There is no separate "verifier" LLM call for the success path — a step's own `ActionResult` (success/failure/`PendingUserAction`/`UserActionRequired`/`UnknownAction`) drives the state machine [`AgentLoop.kt:1017-1067`]. Only an `UnknownAction` result (the requested `action` string isn't registered) triggers `reEvalEngine.replanAfterUnknownAction()`: one more `provider.complete()` call, given the failed step, completed steps and remaining steps as JSON, constrained to a whitelist of valid action names, asking for `{speech, decision:"MODIFY", updatedPlan:{...}}` [`AgentLoop.kt:1082-1100`, `ReEvaluationEngine.kt:83-134`]. The system prompt for *conditional* branches ("if battery < 20% do X") tells the model to schedule every branch's steps up front and rely on this same re-evaluation engine at each step boundary to decide continue-vs-abandon, rather than encoding control flow in the JSON [`PlanningPrompts.kt:29-38`]. Retry/step limits and a fixed cap on iterations were not found in the portions of `AgentLoop.kt` read; `retryRequest()` exists as a user-triggered re-run of a prior failed request rather than an automatic bounded retry [`AgentLoop.kt:331`].
- **History across steps.** History is not carried through a persistent `Conversation`/KV-cache at all in this loop: each of the plan/critic/merge/re-eval calls is an independent `provider.complete()` with its own `messages` list built fresh for that call [`AgentLoop.kt:637-692`, `ReEvaluationEngine.kt:117-133`]. "Memory" across turns is a separate subsystem (`memoryManager.getRelevantContext()`, injected as plain text into the planning system prompt [`AgentLoop.kt:631`]), not engine-level session reuse.
- **Where `LiteRTLMProvider` sits.** Every one of the above LLM calls goes through the same `LLMProvider.complete()`/`streamComplete()` interface, resolved by `llmProviderFactory.getActiveProvider()` [`AgentLoop.kt:630`], which (per the first half of this document) may resolve to `HybridOnDeviceProvider` → `LiteRTLMProvider`. `complete()` is non-streaming end-to-end: it calls `invokeLiteRTInference()`, which builds a fresh `Conversation` from the cached `Engine`, calls `conversation.sendMessage(prompt)` once, reads back `Content.Text` from the returned `Message`, and closes the `Conversation` in `finally` — no partial/streaming output is exposed to `AgentLoop` at all for planning calls [`providers/LiteRTLMProvider.kt:114-141,401-429`]. `streamComplete()` (used elsewhere for the user-facing chat reply, not for planning) does the same fresh-`Conversation`-per-call pattern but collects `conversation.sendMessageAsync(prompt)` as a `Flow<String>`; sampling is fixed at `topK=40, topP=0.95, seed=0` with only `temperature` taken from the request in both paths [`providers/LiteRTLMProvider.kt:161-179,412-419`]. Stop conditions are not passed into `EngineConfig`/`SamplerConfig` in either path — no `stopSequences` field was found reaching the native call.

### termux-launcher: no in-app loop, one API call per turn

No file under `app/src/main/java/com/termux/ai` implements a plan/step/execute/verify loop. `TaiModelCatalog.java:151` and `TaiManager.java:1545` are the only `plan`/`agent` matches, and both are a capability-tag string and a comment about *external* "Agent TUIs" that "attach their complete tool catalogue to even a casual text prompt", respectively — i.e. multi-turn tool use is something an outside client does, not something TAI does to itself. `TaiManager.java` (2208 lines) is the OpenAI/Ollama-compatible HTTP surface: `status()` advertises `/v1/models`, `/v1/chat/completions`, `/v1/responses`, `/v1/completions`, `/v1/embeddings`, plus Ollama's `/api/chat`, `/api/generate`, etc. [`TaiManager.java:165-173`]. `TaiAichatConfig.format()` emits a YAML client-config block (`type: openai-compatible`, `api_base`, `api_key`, per-model `max_input_tokens`) so the third-party `aichat` CLI can point at TAI as a backend [`TaiAichatConfig.java:10-22`], and `TaiCliFormatter.format()` renders TAI's JSON responses for the `tai` CLI command [`TaiCliFormatter.java:14-24`]. `TaiChatRequest.java` models one OpenAI-style request/response pair, not a plan.

- **One call per HTTP turn.** `openAiChatCompletions(body)` parses one OpenAI-style request, resolves the model, builds a `chatRequest`, and calls `localRuntime().chat(modelId, chatRequest.request, options)` exactly once, returning one `chat.completion` [`TaiManager.java:517-566`]. The streaming twin, `openAiChatCompletionsStream(body, sink)`, does the same resolution then calls `localRuntime().chat(modelId, chatRequest.request, options, new TaiGenerationCallback(){...})`, forwarding native `onToken`/`onThinkingToken`/`onToolCalls` events straight into SSE chunks [`TaiManager.java:661-812`]. There is no loop here that issues a second model call based on the first call's output; a second turn only happens if the external client sends another HTTP request (typically with the growing message history appended, per the OpenAI convention).
- **Process boundary.** If called from the app/UI process, both methods first check `shouldDelegateRuntime()` and, if true, forward the whole request over IPC to the isolated `:tai_runtime` process (`runtimeRequest(TaiRuntimeIpc.OP_OPENAI_CHAT, ...)` / `runtimeClient.stream(TaiRuntimeIpc.OP_OPENAI_CHAT_STREAM, ...)`) [`TaiManager.java:517-518,661-667`]; the code shown above (`localRuntime().chat(...)`) is what actually executes once inside that process. `runtimeStatus()` documents this directly: "TAI loads native LiteRT-LM/MNN backends in an isolated Android process after preflight checks" [`TaiManager.java:186`].
- **Generation call itself.** `localRuntime()` resolves to `MultiBackendTaiRuntime`, which routes to `LiteRtTaiRuntime.chat(...)` for LiteRT-LM models [`MultiBackendTaiRuntime.java:13-26`]. `chat()` builds/reuses a `Conversation` via `ensureConversationLocked()` and calls `activeConversation.sendMessageAsync(request.message, new MessageCallback(){...})`, i.e. it is internally streaming even when `TaiManager` is only asked for the non-streaming `openAiChatCompletions` response — the synchronous entry point just collects the callback's tokens into one string before returning [`LiteRtTaiRuntime.java:298-336`].
- **Cancellation.** Stop sequences from the OpenAI `stop` request field are matched app-side, token by token, by `OpenAiStopSequences.StreamMatcher` (132-line helper class) as they stream out of the callback; once matched, `TaiGenerationCallback.shouldCancelGeneration()` returns `true`, which `LiteRtTaiRuntime`'s `MessageCallback.onMessage()` checks to call `activeConversation.cancelProcess()` mid-generation — a genuine native cancel, with a comment noting cancellation "leaves the KV cache dirty" so that conversation is discarded rather than reused afterward [`TaiManager.java:661,721-731,749-758`, `LiteRtTaiRuntime.java:333,368,427-432`, `OpenAiStopSequences.java:14-16`].
- **Tool calls and the thinking channel.** `ToolCall` objects come straight from the SDK on each streamed `Message` (`message.getToolCalls()`) and are forwarded through `TaiGenerationCallback.onToolCalls(JSONArray)` to an `emitToolCallChunk` SSE frame — no text-JSON convention or hand-parsing is involved [`LiteRtTaiRuntime.java:349-356,974-990`, `TaiManager.java:768-782`]. The reasoning/"thought" stream uses the SDK's `Channel` construct (`thinkingChannels()`, e.g. a `"thought"` channel with start/end markers) and is surfaced through a separate `onThinkingToken`/`emitChatThinkingChunk` SSE event, kept apart from the assistant's answer text, and also exposed as `reasoning_content` on the non-streaming response [`LiteRtTaiRuntime.java:965-970`, `TaiManager.java:749-758,580`].
- **History across turns.** `ensureConversationLocked()` keeps the previous request's `Conversation` (and its KV cache) alive and reuses it for the next HTTP turn only if a message-fingerprint check (`TaiConversationTranscript.continuesFrom`) proves the new request's message list is a strict continuation of the one the live conversation already reflects; otherwise the stale conversation is closed and a new one is created [`LiteRtTaiRuntime.java:721-758`, `TaiConversationTranscript.java:43`]. This is the mechanism, not a planning loop, that avoids re-processing the whole transcript on every turn.

### The 4 sharpest differences

1. **A planning loop exists only in opendroid.** `AgentLoop`/`PlanManager`/`ActionSequenceExecutor`/`ReEvaluationEngine` (opendroid) turn one user goal into a whole JSON plan and mechanically execute+replan it [`AgentLoop.kt:628,945,1082`]; termux-launcher has no such file — `TaiManager` only answers one OpenAI-style HTTP turn at a time [`TaiManager.java:517,661`], and any multi-step "agent" behavior is left to an external CLI ("Agent TUIs", `aichat`) that termux-launcher only formats config/output for [`TaiAichatConfig.java:10`, `TaiCliFormatter.java:14`].
2. **KV-cache/conversation reuse is opposite.** termux-launcher deliberately keeps a `Conversation` alive across HTTP turns when a fingerprint proves continuity, to preserve the KV cache [`LiteRtTaiRuntime.java:721-758`]; opendroid's `LiteRTLMProvider` closes and recreates a `Conversation` on every single `complete()`/`streamComplete()` call, including every planner/critic/merge/re-eval call inside one `AgentLoop` turn, so each of those calls reprocesses its whole flattened prompt from a cold KV cache [`providers/LiteRTLMProvider.kt:166-179,412-429`].
3. **Tool calls: native SDK object vs. in-band JSON convention.** termux-launcher reads `ToolCall` off the SDK's `Message` directly [`LiteRtTaiRuntime.java:349`]; opendroid's `LiteRTLMProvider` asks the model, via its own prompt text, to emit `{"toolCall":{"name":...,"arguments":...}}` and then hand-parses that JSON out of the response text [`providers/LiteRTLMProvider.kt:211-215,470-482`] — the *same* underlying LiteRT-LM SDK is used two structurally different ways, one relying on a native contract, the other on the model obeying a prompt convention.
4. **Cancellation is a native call vs. absent from the LLM path.** termux-launcher's stop-sequence match calls the SDK's `conversation.cancelProcess()` mid-stream [`LiteRtTaiRuntime.java:368`]; no equivalent call was found anywhere in opendroid's `LiteRTLMProvider.kt`, `AgentLoop.kt`, or `ReEvaluationEngine.kt` — `AgentLoop`'s own cancellation (`cancelCurrentTask()`, `AgentLoop.kt:849`) is a coroutine-cancellation checkpoint between plan steps, not a call into the LiteRT-LM engine to stop an in-flight generation.

### Plain-language summary

The two codebases fit the framing the task proposed: **opendroid is agent-in-app** — one part of the app (`AgentLoop`) decides the whole multi-step plan, hands each step to on-device automation code, and only calls the model again if a step's action name isn't recognized. **termux-launcher is runtime-as-service** — `TaiManager` answers one OpenAI-style request at a time and does not decide what happens next; a caller (an external CLI, an "Agent TUI", or ultimately a person) has to send the next request itself, including any multi-step tool-use loop. Nothing found in either codebase during this pass contradicts that framing.
