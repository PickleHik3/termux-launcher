# Desktops: install, remove and open whole Linux desktops (2026-11-26)

Decided with the developer on 2026-11-26 (issue #394). Research:
[`docs/research/wayland-desktops-in-a-window-2026-11-26.md`](../../docs/research/wayland-desktops-in-a-window-2026-11-26.md).
The runtime folder rule is [ADR 0036](../../docs/adr/0036-every-shell-shares-one-runtime-folder.md).
Words (**desktop**, **Linux app**, **Linux window**, **X11 Display**, **Wayland Display**, **rim
tab**) are the glossary's.

## Problem Statement

A user who wants a whole Linux desktop on the launcher has one choice, made once: the set-up guide
has a single Desktop tick, which means XFCE. After that first set-up there is nowhere to add a
second desktop, see which are installed, or remove one. Trying another desktop means typing package
commands and cleaning up by hand.

A user who wants a Wayland desktop cannot start one at all. They follow sway's or labwc's own
guide, type its command in a launcher terminal, and it stops with an error about a missing runtime
folder. Nothing in the launcher or its docs says why, or which desktops can work on a phone.

Where a Linux app opens is one setting for every app. An app that only behaves on X11 Display
forces every other app back there, and a user cannot compare the two displays, or two graphics
choices, without changing everything at once.

Wayland Display itself is in no released build, so none of what it adds has reached a user.

## Solution

Settings › Linux apps gains a **Desktops** page. It lists the desktops the launcher can install,
each marked Install or Installed. A tap on Install runs the install by itself, with a small
watch-only terminal opening under the row so the user sees it working. An installed desktop's row
opens its settings, where it can be removed, with or without the settings it wrote.

Several desktops can be installed side by side; one runs at a time. Each appears in the drawer with
the Linux apps and opens as it does today: on the display under X11 Display, as one Linux window
under Wayland Display.

Every Linux app's settings page gets a **Display** row, so one app can be sent to the other
display while the rest follow the main setting. Each X11 desktop also gets a **Graphics** row with
every graphics choice, so a user can compare desktops and drivers on their own phone.

Every shell gets one shared runtime folder, so a Wayland desktop started the way its own guide
says simply starts. sway and labwc join the Desktops list once a test on pong shows they hold up.
A page in the user docs says which desktops work and why Hyprland and Plasma's Wayland session
cannot.

Wayland Display is built into ordinary builds from the next pre-release drop. X11 Display stays the
default.

## User Stories

Finding and installing

1. As a user, I want a Desktops page under Settings › Linux apps, so that I can see every desktop the launcher offers in one place.
2. As a user, I want each desktop's row to say Install or Installed, so that I know what I have without opening a terminal.
3. As a user, I want to install a desktop with one tap, so that I never paste a command.
4. As a user, I want to see the install running in a small terminal under the row I tapped, so that I know it is working and roughly how far along it is.
5. As a user, I want that terminal to be for watching only, so that a stray touch cannot break the install.
6. As a user, I want the terminal's text small enough that whole lines fit, so that the output is readable without scrolling sideways.
7. As a user, I want the row to close to Installed when the install finishes, so that the list returns to rest by itself.
8. As a user, I want a failed install to keep its terminal open with the error, so that I can read what went wrong or show it to someone.
9. As a user, I want to try a failed install again from the same row, so that a dropped connection does not send me back to the start.
10. As a user, I want an install to carry on if I leave the page, so that I can use the phone while a large download runs.
11. As a user, I want the page to show the right state when I come back, so that I am not told to install something already installing.
12. As a user, I want only one install or removal to run at a time, so that two package operations never collide.
13. As a user, I want to install XFCE, LXQt, MATE and Plasma from the list, so that I can pick the desktop I know.
14. As a user, I want a newly installed desktop to appear in the drawer with my Linux apps, so that opening it is the same as opening any app.
15. As a first-time user in the set-up guide, I want to pick which desktop to add from the same list, so that the guide and the Desktops page agree.
16. As a user who set up XFCE before this existed, I want it to show as Installed, so that the page reflects what is on my phone.
17. As a user with a desktop inside a proot-distro container, I want it listed as installed with its distro's name, so that the page shows every desktop I can open.
18. As a user, I want a container desktop's row to open its settings but offer no Install or Remove, so that the page does not promise what it cannot do there yet.

Removing

19. As a user, I want to remove a desktop from its settings page, so that I can free space without knowing its package names.
20. As a user, I want Remove to ask before it acts, so that a slip does not uninstall a desktop.
21. As a user, I want removal to take the packages that desktop brought and nothing I installed myself, so that removing a desktop never breaks my other apps.
22. As a user with two desktops that share a package, I want removing one to leave the other working, so that trying desktops side by side is safe.

27. As a user, I want to watch a removal in the same small terminal, so that removal is as visible as install.
28. As a user, I want a removed desktop to leave the drawer, so that I am not left with an entry that fails.

30. As a user, I want several desktops installed at once, so that I can try different ones on different days.

35. As a user, I want closing a desktop's window to end the desktop, and a desktop that ends to close its window, so that nothing keeps running unseen.

53. As a user, I want an X11 desktop to have the same Display row, so that I can open XFCE on the display or as a Linux window.

56. As a user, I want a desktop's Graphics row to default to following the main graphics setting, so that nothing changes until I choose.

58. As a user on a build without Wayland Display, I want no Display row and no Wayland desktops, so that I am not shown choices that do nothing.

Knowing what works

59. As a user who wants Hyprland, I want the docs to say plainly that it cannot run on Android and why, so that I stop looking for a way.
60. As a user who wants Plasma, I want to know its X11 desktop is in the list and its Wayland one is not, so that I install the one that works.
61. As a user thinking a container would help, I want the docs to say a container does not change this, so that I do not spend an evening finding out.
62. As a tester on the pre-release channel, I want Wayland Display in the build I already get, so that I can try Linux windows and report on them.

Keeping it honest

68. As a user who never opens a Linux app, I want my launcher to start as fast as before and hold no more memory at rest, so that this feature costs me nothing.

## Implementation Decisions

**A desktop catalogue, one deep module.** One table defines every desktop the launcher knows:
name, kind (made for X11 or for Wayland), the packages it needs, the files that prove it is
installed, the folders in the user's home that hold its settings, the command its own
documentation starts it with, and for Wayland desktops a starter config. It is pure: callers hand
it a way to test for files and get answers back. It answers:

- the state of each desktop (not installed, installed, installed in a container);
- the script Install runs and the script Remove runs;
- the starter config text and where it goes;
- whether a desktop is offered at all in this build.

The existing XFCE package list and its piece-by-piece detection move behind it; the set-up guide's
Desktop starter and the Desktops page both read it. "Installed" is decided from files, never from
a package database, because Termux installs are apt-based or pacman-based and the two disagree on
revisions.

**The first entries** are XFCE, LXQt, MATE and Plasma (X11), all from Termux's own packages. sway
and labwc are entries too, held back by one switch in the catalogue until the pong test passes
(see Testing Decisions). Hyprland, Plasma's Wayland session and niri are not entries.

**Install** is one generated script per desktop, run the way the first-run Setup card runs its
install: a headless terminal session that is not one of the user's sessions. Before installing, the
script records which of the desktop's packages are not yet present; that record is the desktop's
manifest and lives with the launcher's other set-up state in the prefix. For a Wayland desktop the
script then writes the starter config, only when the user has no config for that desktop.

**Remove** uninstalls the packages in the desktop's manifest, less any that another installed
desktop's manifest or the starter apps still claim, together with dependencies nothing else needs.
It never removes a package the user installed by name. It works for both package managers. A
desktop installed before manifests existed (today's XFCE) is removed by its catalogue package list
under the same "still claimed" rule. With the tick set, it also deletes the settings folders the
catalogue lists for that desktop, which include a starter config the launcher wrote. A running
desktop is stopped first, after the confirm.

**One run at a time.** While an install or removal runs, every other Install and Remove on the
page is unavailable. The run does not belong to the page: leaving Settings does not stop it, and
the page shows the live state on return.

**The install view.** The row being installed or removed grows a small terminal beneath it. It is
the read-only terminal the Graphics acceleration page already uses for its benchmark (no cursor,
no focus, font fitted to a fixed column count), lifted out so both pages share it. It closes when
the run succeeds and stays open on failure with the row offering to try again. Its transcript is
bounded, and the view and its session are released when the row closes.

**Container desktops** are listed from what the Linux app catalogue already finds in proot-distro
containers, shown as installed with the distro's name. Their rows open their settings; the page
does not install or remove them, and the guide's "A full Linux" route keeps doing that.

**The set-up guide.** On the Termux route its Desktop tick becomes a pick from the catalogue (none,
or one desktop). The container route keeps XFCE.

**Which display a launch uses** stays one pure function, extended. Its inputs are the main
setting, the app's own choice (Default, X11 Display, Wayland Display), whether the launch is a
desktop and of which kind, whether it is inside a container, and whether the build has Wayland
Display. Its rules:

- a build without Wayland Display always answers X11 Display;
- a desktop made for Wayland always opens under Wayland Display, whatever the main setting;
- a desktop inside a container opens on X11 Display, as now;
- otherwise the app's own choice wins, and Default follows the main setting.

Nothing else branches on the stored values.

**The main setting no longer stops anything.** Changing it affects the next launches only; windows
already open stay. Both displays can therefore be running at once. This replaces today's
behaviour, where choosing X11 Display stops the Wayland Display host.

**The Wayland Display socket** is owned whenever the build has Wayland Display, not only while it
is the main setting, since any app may be pinned to it. The host still starts on the first
connection and stops when idle. The variables new shells receive keep following the main setting,
as now.

**Per-app settings.** The per-app store gains the display choice. For X11 desktops the existing
per-app graphics field is honoured (today a desktop always takes the display's profile) and the
row lists every profile after "Follow display setting". Ordinary apps keep their two-entry
Graphics row. Rows by kind:

| | Display | Graphics | Touch mode | Scale, Paste shortcut | Show in app drawer | Remove |
|---|---|---|---|---|---|---|
| Linux app | yes | two entries, as now | yes | yes | yes | no |
| X11 desktop (Termux) | yes | all profiles | yes | no, as now | yes | yes |
| Wayland desktop | no | no | yes | no | yes | yes |
| Desktop in a container | no | no, as now | yes | no | yes | no |

**One runtime folder (ADR 0036).** The launcher writes a default for `XDG_RUNTIME_DIR` (the
prefix's tmp folder) that fills the variable only when it is empty, for the sh family through the
prefix's profile folder and for fish through its start-up folder. The files are written at launcher
start, before the first shell is opened, and are rewritten only when their text differs. Launches
the launcher makes itself carry the same value, so an app opened from the drawer agrees with a
shell. Inside a container the profile file the launcher already writes there gains a default of
the container's own: a private folder under the container's tmp, created at login; the value the
runner gives a container desktop today becomes that same folder.

**Starting a Wayland desktop.** The catalogue's start command is the desktop's own (`sway`,
`labwc`), run with the shell's environment and no wrapper. The Linux app catalogue reads Wayland
desktop entries beside the X11 ones, so a Wayland desktop the user installed by hand is listed
too. No fence is needed: a Wayland desktop hands its own socket to the apps inside it. The
one-desktop rule covers both kinds through the gate that exists.

**A desktop's window under Wayland Display.** It is a Main window told the pane's size in its
first configure. A Wayland desktop's window is sized in real pixels (scale 1), as the X11
desktop's window already is, because these desktops ignore the host's scale; the desktop's own
scale comes from its config. The starter config sets that scale once, from the Linux windows scale
at install time. The rim tab of a Wayland desktop has no Scale item; an X11 desktop keeps its live
Scale. Every desktop's rim tab gains Full screen, using the full-screen behaviour already decided
(chrome hidden, Back leaves, swipe up from the bottom edge shows the extra keys). The launcher
recognises a desktop it started by its launch tag. A desktop the user typed in a terminal is
recognised only if its windowed mode announces itself in a way the host can read; otherwise it is
an ordinary window and the user sets its scale as its guide says.

**Shipping.** CI builds the compositor into ordinary builds for the next pre-release drop. The
Display setting appears with X11 Display selected and its existing hint. Which editions carry it
is decided when the drop is cut.

**User docs.** One page in the user guides: which desktops work, that sway and labwc draw without
the graphics chip, how to install and remove, and that Hyprland and Plasma's Wayland session need
a graphics device Android gives no app, in a container as well.

**Copy.** The page is "Desktops". Row states are "Install", "Installing…", "Installed". The
settings row is "Remove", its confirm "Remove XFCE?" with "Also delete its settings". No package,
protocol or driver words in any string.

## Testing Decisions

A good test here states a rule a user would notice broken (the wrong package removed, the wrong
display opened, a shell without the folder) and checks the answer of a pure function. It does not
assert on generated text beyond the lines that carry the rule, and it does not reach into a view.

Three seams carry the tests, agreed with the developer:

1. **The desktop catalogue.** State from a supplied file test; the install script (packages,
   manifest written before installing, starter config only when none exists); the remove script
   (manifest less what other manifests and the starter apps claim; settings folders only with the
   tick; both package managers; a pre-manifest XFCE); the held-back switch for sway and labwc; the
   guide and the page reading the same entries. Prior art: the tests of the set-up script
   generator and of the XFCE pieces detection.
2. **The launch decision.** Every combination of main setting, per-app choice, desktop kind,
   container and build, as a table. Prior art: the existing test of that function, which grows.
3. **The runtime folder files.** The sh and fish texts; "only when empty"; the container's
   variant; that an unchanged file is not rewritten. Prior art: the test of the display profile
   written into containers.

Smaller tests ride on seams that exist: the Linux app catalogue reading Wayland desktop entries
(its test currently asserts they are not read, and flips); the per-app graphics pick for a desktop;
the per-app store's new field; the rim tab's items for a desktop; the page's state rules (one run
at a time, failed keeps the terminal) in the style of the Setup card's logic test.

Not unit tested, checked on a device: the Desktops page and its rows, the terminal under the row,
a real install and removal of each desktop on both package managers, the first open of each
desktop under each display, Full screen and its way out.

**The pong test that admits sway and labwc.** Four set-ups: XFCE on X11 Display (the graphics-chip
baseline), XFCE under Wayland Display, sway, labwc. Each gets the same actions: open a terminal,
scroll a long file, move a window, load a web page. Memory at rest and CPU during each action are
recorded for the desktop, the compositor process and the launcher. sway and labwc are admitted
when they use no more CPU and memory than XFCE under Wayland Display, touch lands where the finger
is, the Super key reaches them from the launcher keyboard and from a hardware keyboard, and the
developer finds them as smooth by eye. The figures go in the verification docs. The research
note's checks 1, 4, 5, 6 and 7 are part of this round.

Owed on a device beyond that: whether a desktop's graphics choice takes effect under Wayland
Display (if it does not, the Graphics row hides when the desktop resolves to Wayland Display);
the prefix tmp folder's permissions; a launcher start with the runtime files in place before the
first restored session; Herdr with every shell on the shared folder.

## Out of Scope

- Hyprland and Plasma's Wayland session, including any fork or patch of them.
- niri, and installing or removing a desktop inside a container from the Desktops page.
- A graphics-chip path for sway and labwc (a patch to their shared library); decided after the
  pong figures.
- Two desktops running at once.
- Making Wayland Display the default, or removing X11 Display.
- Panels or wallpapers of a desktop attaching to the launcher's own screen.
- A display manager, and desktop items in tlstore.
- A way into per-app settings from the drawer.
- A fuller Graphics row for ordinary Linux apps.
- The extra protocols only Hyprland or KWin would need.

## Further Notes

- **Order of work.** The runtime folder and the launch decision first: they are small and
  everything else leans on them. Then the catalogue with the four X11 desktops and the Desktops
  page. The Wayland desktop pieces (catalogue reading, real-pixel sizing, starter config) and the
  pong test can run beside the page; the four X11 desktops do not wait for sway and labwc.
- **Two behaviours change on purpose:** the main Display setting no longer stops running windows,
  and a desktop no longer always takes the display's graphics profile.
- **A correction to the Wayland Display spec.** It says a Wayland-native desktop such as KWin
  "would run nested the same way". The research shows labwc does and KWin does not.
- **Superseded when built:** the "never set" lines about `XDG_RUNTIME_DIR` in the Linux apps agent
  doc and the Wayland Display spec.
- **For the developer to decide when it comes up:** which editions get Wayland Display in the drop;
  what the Desktops page offers on an edition whose packages do not come from Termux's
  repositories.
- **Surfaces to cover when building:** both package managers; both displays; a build with and
  without Wayland Display; a desktop in the prefix and in a container; fish and sh shells; light,
  dark and black themes on the new page; large font scale on the rows and the terminal.
