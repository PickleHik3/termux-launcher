First, a correction

I told you the wrong reason earlier today

What I said, and what is actually true

I said the blocker was the Type=XSession field. It is not. Of the nineteen desktops in Termux's X11 repo, eleven mark their session file Type=Application — xfce, LXQt, MATE and openbox among them — exactly like any ordinary app. Seven use XSession, and one says nothing at all.

The real reason is duller: the launcher only ever looks in one folder. Apps live in share/applications; desktops put their session file in share/xsessions, and nothing has ever read that folder. Hand xfce.desktop to today's filter unchanged and it would sail through.

So the plumbing is smaller than I made it sound. The work is in the policy — which is what the questions below are about.

What is true

Read out of the actual packages, not guessed

  • Sessions live one folder over.$PREFIX/share/xsessions in Termux, /usr/share/xsessions inside a distro container. The launcher scans neither.
  • Only one window manager may run on a screen.That is the X protocol itself, not a setting — a second one gets an Access error and dies. The launcher already runs openbox alongside every display.
  • LXQt is polite about it. XFCE is not.LXQt checks whether a window manager is there and skips its own. XFCE starts xfwm4 regardless; xfwm4 finds openbox, says so, and quits — the panel, Thunar and the desktop still come up, but under openbox's maximise-everything rule.
  • XFCE needs a message bus and starts none.LXQt and MATE each start their own. dbus is in Termux's main repo, not the X11 one, so it may not even be installed.
  • Most desktops ship no icon.Ten of nineteen have an Icon key and four of those are empty. Only openbox and IceWM name a real one.
  • A refused session would be retried as an Electron crash.A live bug: anything that exits non-zero within three seconds gets retried with --no-sandbox. A session refused because openbox holds the display does exactly that.
